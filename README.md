## Задание 1. Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

* облачная система;
* система контроля версий Git;
* репозиторий на каждый сервис;
* запуск сборки по событию из системы контроля версий;
* запуск сборки по кнопке с указанием параметров;
* возможность привязать настройки к каждой сборке;
* возможность создания шаблонов для различных конфигураций сборок;
* возможность безопасного хранения секретных данных (пароли, ключи доступа);
* несколько конфигураций для сборки из одного репозитория;
* кастомные шаги при сборке;
* собственные докер-образы для сборки проектов;
* возможность развернуть агентов сборки на собственных серверах;
* возможность параллельного запуска нескольких сборок;
* возможность параллельного запуска тестов.

Обоснуйте свой выбор.

## Решение

Основные решения на рынке:

Комплексные DevOps-платформы:

*  GitLab. Git-репозитории, CI/CD, Container Registry, управление секретами, шаблоны Pipeline, Runner. Универсальное решение. Облачный сервис и Self-Managed, в т.ч. бесплатный.
*  GitHub Enterprise + GitHub Actions. Хранение Git-репозиториев, автоматизация CI/CD через Workflows, собственные Self-hosted Runners, Packages и Container Registry. Облачный и Enterprise-варианты.
*  Bitbucket + Bitbucket Pipelines. Git-репозитории, CI/CD Pipelines, собственные Docker-образы, переменные окружения и интеграция с Jira.
*  Azure DevOps. Azure Repos (Git), Azure Pipelines, Artifacts, Boards, Test Plans. Облачная и Server-версии. Сильная интеграция с Microsoft Azure и корпоративной инфраструктурой.

Специализированные CI/CD-системы. Эти продукты обычно не заменяют Git-хостинг. Они подключаются к существующим Git-репозиториям:

*  TeamCity (JetBrains). Конфигурации сборок, шаблоны, Build Agents, параметры запуска, артефакты, параллельные сборки. SaaS и Self-Hosted. Сильная система управления конфигурациями сборок.
*  Jenkins. Одна из наиболее известных систем автоматизации сборки. Pipeline as Code (Jenkinsfile), плагины, собственные агенты, Docker, Kubernetes. Но нет официального облачного решения.
*  CircleCI. CI/CD для GitHub и Bitbucket, собственные Docker-образы, reusable Config, Executors, Self-hosted Runners. Облачный сервис и варианты размещения собственных Runner.
*  Buildkite. Облачная управляющая платформа с агентами сборки в инфраструктуре компании. Поддерживает параллельные задания, плагины, Docker и различные конфигурации Pipeline.

Cloud-native и Kubernetes-ориентированные решения:

*  Tekton. Open Source CI/CD-платформа, построенная на Kubernetes.
*  AWS CodePipeline + AWS CodeBuild. Управляемая облачная система сборки и доставки приложений. Интеграция с Git-провайдерами. Подходит прежде всего компаниям, использующим AWS.

Выделю три наиболее подходящих варианта, которые обеспечивают все указанные в задании требования:

* **GitLab**. Максимально простая в использовании единая архитектура
* **GitLab + TeamCity**. Сильные возможности управления конфигурациями сборок
* **GitHub Enterprise + Actions**. Современная облачная DevOps-платформа

TeamCity — один из наиболее интересных конкурентов в части GitLab CI/CD с точки зрения перечисленных требований задания. Решение может быть таким: Gitlab отвечает за хранение исходного кода, а TeamCity за CI/CD. Однако это требует работы двух продуктов и их интеграции, а также оплаты за два SaaS, что несколько усложняет решение.

Если сравнивать GitLab и "GitHub Enterprise + Actions", то оба решения полностью соответствуют требованиям задания и позволяют построить облачную CI/CD-инфраструктуру для микросервисной архитектуры, при этом в рамках одного провайдера SaaS.

В пользу Gitlab говорит следующее:
* Все необходимые компоненты находятся в одной платформе.
* Простота централизованного управления CI/CD. 
* GitLab Runner позволяет организовать собственную масштабируемую инфраструктуру сборок.
* Централизованные CI/CD-шаблоны удобны для стандартизации процессов в крупной компании с большим количеством микросервисов.

И я бы посчитал важным возможность перейти с облачного на Self-Hosted решение. И тут в GitLab можно воспользоваться бесплатным Self-Hosted. А вот в GitHub он будет платным.

В части безопасного хранения секретных данных - для крупной компании рекомендуется интеграция с HashiCorp Vault. Это позволяет не хранить постоянные секреты непосредственно в GitLab. Можно воспользоваться SaaS или Self-Hosted.

### Итог: выбираем GitLab + Vault

## Задание 2. Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

* сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
* минимальные требования к приложениям, сбор логов из stdout;
* гарантированная доставка логов до центрального хранилища;
* обеспечение поиска и фильтрации по записям логов;
* обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
* возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

## Решение

Основные известные инструменты в виде таблицы:

| № | Требование | ELK Stack | Grafana Loki | Graylog | VictoriaLogs | OpenSearch |
|---|---|---|---|---|---|---|
| 1 | Сбор логов в центральное хранилище со всех хостов | Да | Да | Да | Да | Да |
| 2 | Минимальные требования к приложениям, сбор из stdout | Да | Да | Да | Да | Да |
| 3 | Гарантированная доставка логов до центрального хранилища | Да, Kafka + дисковая буферизация | Да, WAL + буферизация; Kafka дополнительно | Да, Journal + буферизация агента | Да, дисковая буферизация агента | Да, Kafka + дисковая буферизация |
| 4 | Поиск и фильтрация по записям логов | Да | Да | Да | Да | Да |
| 5 | Web UI и разграничение доступа разработчиков | Да | Да | Да | Да, через vmauth или Grafana | Да |
| 6 | Возможность предоставить ссылку на сохранённый поиск | Да | Да, через Grafana | Да | Через Grafana; собственный Web UI имеет более ограниченные возможности | Да |

В пункте "**Гарантированная доставка**" элемент Kafka — дополнительный уровень надёжности, а не обязательное условие. Можно рассмотреть архитектуру без Kafka: она будет проще и дешевле в эксплуатации. Без Kafka будут такие решения:

| Решение	| Гарантированная доставка |
|---|---|
ELK | Да, при настройке persistent queue и повторной отправки
Grafana Loki | Да, с оговорками по WAL Alloy и WAL Loki
Graylog | Да, при настройке дисковой буферизации и надёжного протокола
VictoriaLogs | Да, Vector с дисковым буфером и at-least-once (документированная гарантия)
OpenSearch | Да, при настройке дисковой буферизации и подтверждений

### Рассмотрим все 5 решений.

**Grafana Loki** — ориентирован преимущественно на поиск по меткам (labels), а не на полноценную полнотекстовую индексацию. Для сложного поиска и фильтрации логов ELK и OpenSearch предоставляют более широкие возможности. Сохранённые запросы реализуются средствами Grafana.

**Graylog** — Имеет ограничения по функциональности в бесплатной редакции. Имеет более специализированную архитектуру и дополнительные обязательные зависимости (MongoDB и Data Node). Graylog в большей степени ориентирован на централизованное управление логами и SIEM, тогда как Elastic Stack предоставляет более широкую экосистему инструментов для observability и аналитики. 

**VictoriaLogs** — более молодая экосистема, уступает ELK/OpenSearch по возможности управления сохранёнными поисками и пользовательскими доступами, и по зрелости инструментов, интеграций. Для совместного использования сохранённых запросов нужна Grafana. Однако это интересный вариант с точки зрения **производительности, стоимости хранения** (эффективное сжатие) и простоты эксплуатации.

Указанные выше 3 системы отметаем, так как условиям больше соответствуют **OpenSearch** и **ELK**.

Если сравнивать **OpenSearch** и **ELK** именно с точки зрения требований задания, то оба варианта удовлетворяют всем поставленным условиям.

Преимущества **OpenSearch** заключаются в Open-source лицензии (Apache 2.0) и полном наборе инструментов без коммерческой подписки.

Однако преимущество **Elastic** заключается в более широкой функциональности, широте экосистемы и интеграций. Подробнее:

* Более развитая экосистема. Elastic Agent, Fleet, Beats, Logstash, Kibana и интеграции с большим количеством систем.
* Elastic Observability. Более развитые возможности объединения логов, метрик, распределённых трассировок.
* Аналитика. ML-функции и инструменты обнаружения аномалий.
* Управление агентами. Fleet позволяет централизованно управлять Elastic Agent на большом количестве серверов.

**Вариант 1. Elastic Stack** плюс Kafka

Предпочтителен по функциональности. Это зрелое решение с развитой экосистемой и широкими возможностями анализа логов. Если нет ограничений по лицензированию и в будущем допускается использование платных коммерческих возможностей, стоит выбрать именно его.

Архитектура решения:

Elastic Agent / Filebeat → Kafka → Logstash → Elasticsearch → Kibana

**Вариант 2. OpenSearch** плюс Kafka

Предпочтителен по лицензированию. Если требуется полностью открытый стек под лицензией Apache 2.0, без зависимости от лицензионной политики Elastic.

Архитектура решения:

Fluent Bit → Kafka → Data Prepper → OpenSearch → OpenSearch Dashboards

### Итог: выбираем Elastic Stack + Kafka

Выбор по условиям задачи, без учета лицензии. Kafka добавляем как гарантированный способ доставки.

## Задание 3. Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

* сбор метрик со всех хостов, обслуживающих систему;
* сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
* сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
* сбор метрик, специфичных для каждого сервиса;
* пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
* пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

## Решение

Основные варианты решений:

| Решение | Сбор метрик | Хранение | Аналитика и визуализация | Особенности |
|---|---|---|---|---|
| Prometheus + Grafana | Prometheus Exporters, агенты | Prometheus TSDB | Grafana, PromQL | Стандарт де-факто для Kubernetes и микросервисов |
| VictoriaMetrics + Grafana | vmagent, Prometheus Exporters | VictoriaMetrics | Grafana, MetricsQL | Эффективное хранение, горизонтальное масштабирование |
| Zabbix | Zabbix Agent, SNMP, API | Встроенная БД | Собственный Web UI | Хорош для инфраструктурного мониторинга, менее удобен для современной микросервисной observability |
| Datadog | Агенты, интеграции, API | SaaS-платформа | Собственный Web UI | Полноценная коммерческая observability-платформа |
| Elastic Stack | Elastic Agent, Beats, интеграции | Elasticsearch | Kibana | Сильная аналитика для логов; мониторинг метрик также поддерживается |
| Grafana Cloud | Grafana Alloy, Prometheus, OpenTelemetry | Облачная платформа | Grafana | Управляемый SaaS-вариант |
| InfluxDB + Telegraf + Grafana | Telegraf | InfluxDB | Grafana, InfluxQL/Flux | Универсальная система сбора и хранения временных рядов |

**Основные кандидаты:**

1. **Prometheus + Grafana**

Преимущества:
- Широкая поддержка интеграций и exporters.
- PromQL для запросов, фильтрации и агрегации.
- Отличная интеграция с Kubernetes.
- Большая экосистема готовых дашбордов.

Недостаток: при крупной распределённой инфраструктуре централизованное хранение и масштабирование Prometheus требуют дополнительных компонентов. Самостоятельные экземпляры Prometheus не образуют полноценное централизованное хранилище.

2. **VictoriaMetrics + Grafana**

Преимущества:
- Совместимость с экосистемой Prometheus.
- Поддержка PromQL-совместимых запросов через MetricsQL.
- Эффективное сжатие и хранение временных рядов.
- Возможность горизонтального масштабирования.
- Поддержка длительного хранения метрик.
- Возможность использовать vmagent для сбора и отправки метрик.

Недостаток: для построения полноценной системы нужны дополнительные компоненты: агенты, exporters, Alertmanager или аналогичная система оповещений.

3. **Zabbix**

Преимущества:
- Единая система сбора и визуализации.
- Готовые шаблоны для серверов, сетевого оборудования и сервисов.
- Мониторинг доступности, ресурсов и триггеры.
- Подходит для традиционной серверной инфраструктуры.

Недостаток: хуже интеграция с современным стеком Kubernetes и микросервисов, чем у Prometheus-совместимых решений.

4. **Datadog**

Преимущества:
- Единая платформа для метрик, логов, трассировок и APM.
- Большое количество готовых интеграций.
- Не требуется самостоятельно обслуживать хранилище.

Недостаток: стоимость SaaS может существенно увеличиваться с ростом количества хостов, объёма метрик и периода хранения.

---

Стандартное решение "Prometheus + Grafana" — отличный инструмент сбора и локального хранения метрик. Однако при большом количестве хостов и микросервисов возникают дополнительные требования:
- централизованное хранение метрик из разных кластеров;
- длительный срок хранения;
- отказоустойчивость;
- масштабирование при увеличении количества временных рядов;
- разделение данных между подразделениями.

Для решения этих задач VictoriaMetrics предлагает подход с использованием собственного кластерного хранилища и vmagent.

### Для крупной компании выбираем такую архитектуру:

гибрид агентов **Prometheus** и **VictoriaMetrics Cluster**. А именно:

### **VictoriaMetrics Cluster + vmagent + Prometheus Exporters + OpenTelemetry Collector + Grafana**

Логически система состоит из четырёх уровней:
1. Источники метрик — хосты, контейнеры, Kubernetes и приложения.
2. Сбор и передача — exporters, vmagent, OpenTelemetry Collector.
3. Хранение и обработка — VictoriaMetrics Cluster.
4. Визуализация и анализ — Grafana.

Соответствие заданию:

| Требование задания | Реализация | Компоненты | Соответствие |
|---|---|---|---|
| Сбор метрик со всех хостов | Установка агентов на серверы, автоматическое обнаружение источников сбора | Node Exporter, vmagent | Да |
| Сбор метрик CPU, RAM, HDD, Network хостов | Сбор системных метрик операционной системы | Node Exporter | Да |
| Сбор метрик потребляемых ресурсов для каждого сервиса | Сбор метрик контейнеров и процессов с привязкой к конкретному сервису, сгруппированное по Kubernetes namespace, Pod или имени приложения | cAdvisor, kubelet, process-exporter | Да, при соответствующей настройке |
| Сбор специфических метрик сервисов | Использование специализированных Exporters и инструментирование приложений | Prometheus Exporters, OpenTelemetry SDK, Collector | Да |
| Пользовательский интерфейс для запросов и агрегации информации | Выполнение запросов PromQL/MetricsQL, группировка и агрегация метрик | Grafana, VictoriaMetrics | Да |
| Пользовательский интерфейс для настройки панелей | Создание пользовательских дашбордов и панелей мониторинга | Grafana | Да |
